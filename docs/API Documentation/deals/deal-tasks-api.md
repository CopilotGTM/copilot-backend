# Deal Tasks API

This API manages tasks associated with CRM deals and standalone tasks. Tasks can be synced from external CRMs, created by users, or generated by AI agents.

**Base URL**: `/users/crm`

---

## Overview

### Sources

| Source | Value | Description | Mutability |
| --- | --- | --- | --- |
| User-created | `MANUAL` | Tasks created via this API | Read/write |
| CRM-synced | `CRM_SYNC` | Tasks imported from HubSpot/Salesforce | Read-only |
| AI Meeting | `AI_MEETING` | Tasks generated from meeting analysis | Read/write |
| AI Insight | `AI_INSIGHT` | Tasks generated from AI insights | Read/write |

CRM-synced tasks (`integration_id IS NOT NULL`) are read-only — update/delete returns `409 Conflict`.

### Storage Contract

Tasks are read from and written to `crm_tasks`. The unified activity feed uses
`crm_activities` only as a feed-card projection and `crm_activity_links` for
deal/contact/company timeline visibility.

Task due values are enforced at the service layer:

- Timed task: `crm_tasks.due_at` stores the exact UTC date/time and `crm_tasks.due_date`
  stores the derived local calendar date for filtering/display.
- All-day/date-only task: `crm_tasks.is_all_day = true`, `crm_tasks.due_date` is set,
  and `crm_tasks.due_at` is `null`.
- No-due task: both `crm_tasks.due_at` and `crm_tasks.due_date` are `null`.

`due_timezone` is not a `crm_tasks` column and is not accepted as a create/update
request field. When returned, it is server-derived display metadata, normally from
the authenticated user's timezone context.

### Task Scope

Tasks can be:

- **Deal-linked**: Associated with a specific deal via `deal_id`
- **Standalone**: No deal association (`deal_id = null`)

Tasks can be reassigned between deals or detached from deals via the update endpoint.

### Notes

- By default, the global task list is scoped to tasks assigned to the authenticated user. There is no normal-user "all tasks" scope.
- Use `scope=assigned_by_me` to list tasks created by the authenticated user.
- Use `scope=assigned_to_user&assigned_to_key=...` after selecting a specific assignee from `GET /tasks/assignees`.
- By default, completed and cancelled tasks are excluded. Pass `include_completed=true` to include them.
- `is_overdue` is computed server-side: `due_date < now AND status NOT IN (COMPLETED, CANCELLED)`.
- `is_read_only` is computed server-side as `integration_id IS NOT NULL` and is the authoritative flag for whether a task can be edited. PATCH / DELETE / reminder / assign endpoints all return **409 "External CRM tasks are read-only"** when invoked on a read-only task. The frontend MUST gate edit affordances on `is_read_only` (do **not** use `source === "CRM_SYNC"` — `source` is nullable and can drift).
- `deal_name` is resolved from the associated `crm_deals` row (null for standalone tasks).
- Sorting by `due_date` places null due dates last regardless of sort order.
- Assignee filtering follows display precedence: external assignee first, otherwise internal CRM/public owner. This prevents tasks assigned to an external person from appearing under the creator's "assigned to me" list.

## 4. Create Task (Standalone)

```http
POST /tasks
```

Creates a task not linked to any deal (standalone). Optionally link to a deal by including `deal_id` in the body.

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `subject` | string | No* | Task title (max 500 chars) |
| `body` | string | No* | Task description (max 10000 chars) |
| `status` | string | No | Default: `NOT_STARTED` |
| `task_type` | string | No | `TASK` or `TODO` (default: `TASK`) |
| `priority` | string | No | Default: `NONE` |
| `due_date` | string | No | ISO8601 datetime. If `is_all_day=true`, only the local date is stored in `crm_tasks.due_date`; otherwise exact time is stored in `crm_tasks.due_at` and the local date is derived into `crm_tasks.due_date`. |
| `is_all_day` | boolean | No | When `true`, create a date-only task with `due_at=null` |
| `reminder_date` | string | No | ISO8601 datetime |
| `completed_date` | string | No | ISO8601 datetime |
| `owner_user_id` | UUID | No | Assign to an org user |
| `deal_id` | UUID | No | Link to a deal |
| `reminder` | ReminderConfig | No | Configure a reminder |

*At least one of `subject` or `body` is required.

### ReminderConfig

```json
{
  "enabled": true,
  "trigger_time": "2026-03-24T09:00:00Z",
  "recurrence": "NONE",
  "delivery_channel": "teams",
  "timezone": "Asia/Kolkata"
}
```

- `enabled` (required): `true` to create a reminder, `false` to skip
- `trigger_time` (required when enabled): ISO8601 datetime for the reminder
- `recurrence` (optional): `NONE` (default), `DAILY`, `WEEKDAYS`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`
- `delivery_channel` (optional): `teams` or `slack`
- `timezone` (optional): IANA timezone used by the reminder schedule

### Success Response (201)

Returns `TaskDetail`.

### Notes

- `source` is automatically set to `MANUAL`
- `created_by_user_id` is set to the authenticated user
- If the task has an assignee email after create, CopilotGTM sends a best-effort
  assignment email after the task write commits. This applies to internal org
  users and external assignees.
- If `status` is `COMPLETED` and `completed_date` is omitted, it is set to now
- If `status` is not `COMPLETED`, `completed_date` is cleared
- `due_timezone` is not accepted in the request body. Date-only interpretation uses the authenticated user's timezone context.
- `title` is not a task API field. Tasks use `subject` for the task title and `body` for the task description.

## 6. Update Task

```http
PATCH /tasks/{task_id}
```

### Request Body

Any subset of the create fields. Additional update-only capabilities:

| Field | Type | Description |
|-------|------|-------------|
| `deal_id` | UUID \| null | Set to reassign deal, set to `null` to detach |
| `reminder` | ReminderConfig | Create, update, or cancel a reminder |

### Reminder Lifecycle

| Action | Request |
|--------|---------|
| Create reminder | `{ "reminder": { "enabled": true, "trigger_time": "...", "recurrence": "NONE" } }` |
| Update reminder | Same as create — existing reminder is rescheduled |
| Cancel reminder | `{ "reminder": { "enabled": false } }` |

### Notes

- `task_type`, `status`, and `priority` cannot be set to null
- If `completed_date` is provided, the task status is set to `COMPLETED`
- If `status` is not `COMPLETED`, `completed_date` is cleared
- Reassigning a task sends a best-effort assignment email to the new assignee
  after the update commits. Other updates to an assigned task send a best-effort
  task-update email to the current assignee.
- CRM-synced tasks are read-only — returns `409 Conflict`
- Cancelling a reminder unschedules it from Redis and marks it as `CANCELLED`

### Success Response (200)

Returns `TaskDetail`.

### Error Responses

| Code | Condition |
|------|-----------|
| 404 | Task not found |
| 409 | Task is CRM-synced (read-only) |

## 7. Delete Task

```http
DELETE /tasks/{task_id}
```

### Notes

- Soft deletes the task (`is_deleted = true`)
- Any active reminders linked to the task are automatically cancelled
- CRM-synced tasks are read-only — returns `409 Conflict`

### Success Response (200)

Returns `TaskDetail`.

### Error Responses

| Code | Condition |
|------|-----------|
| 404 | Task not found |
| 409 | Task is CRM-synced (read-only) |
