# Deal Task Agent Design

> Historical note: this design predates the task/note source-table migration.
> Current runtime code should use `crm_tasks` / `CRMTask` for task source rows
> and treat `crm_activities` / `CRMActivity` as the feed projection only.

## Goal

Create a post-meeting deal task agent that runs after the existing meeting summary and deal
insight pipeline. The agent reads the generated meeting summary plus current deal context, creates
deal-scoped tasks, and marks existing deal tasks complete when the summary clearly shows they were
completed.

## Decisions

- Use a dedicated `DealTaskAgent`.
- Give the agent direct-write tools: `list_deal_tasks`, `create_deal_task`, and
  `complete_deal_task`.
- Keep write safety in deterministic backend services, not in prompt text alone.
- Run the agent after meeting summaries, deal memory, risk/blocker extraction, and stakeholder
  analysis.
- Do not block task creation when no owner or assignee can be resolved. Create the task on the deal
  with source metadata.
- Defer notification-recipient rules. The task write result should expose enough information for a
  later notifier to message Teams, Slack, or WhatsApp.

## Existing Code Context

- Task API and UI writes use `src/service/crm/internal/tasks_write_service.py`.
- The chat task tool in `src/agents/tools/tasks/create_task.py` is preview-confirm and channel-only.
  It is not suitable for unattended post-meeting automation.
- Task records are `CRMActivity` rows in
  `src/domain/models/organisation_tables/sync/crm/activities.py`.
- `CRMActivitySource` already includes `AI_MEETING` and `AI_INSIGHT`.
- Meeting summaries are generated by
  `src/workers/deal_worker/tasks/meeting_insight_tasks/meeting_summary_task.py`.
- The deal insight pipeline is centralized in
  `src/workers/deal_worker/utils/pipeline_dispatch.py`.

## Architecture

```text
meeting summary jobs
  -> deal_memory.process_job
  -> group(
       risk_blocker.extract_deal_risks_blockers_task,
       stakeholder.analyze_deal_stakeholders_task
     )
  -> deal_tasks.sync_from_summary
```

The final `deal_tasks.sync_from_summary` job runs a `DealTaskAgent` for one deal. It is deal-scoped
and organization-scoped through `AgentContext`, matching the existing immutable-boundary pattern.

## Components

### DealTaskAgent

Location: `src/agents/workflows/deal_tasks/`

Responsibilities:

- Read existing deal tasks first.
- Read meeting summaries and deal context through scoped tools.
- Extract concrete task creation candidates from the meeting summary.
- Complete existing tasks only when completion evidence is explicit.
- Use direct-write tools for all mutations.
- Return a structured result with created, completed, skipped, and failed counts.

### Deal Task Tools

Location: `src/agents/tools/tasks/`

Tools:

- `list_deal_tasks`: returns editable and read-only task context for the current deal.
- `create_deal_task`: creates an internal `AI_MEETING` task linked to the current deal.
- `complete_deal_task`: marks a same-deal internal task as completed.

The tools must never accept `organisation_id` or arbitrary `deal_id` as model-controlled
parameters. They use `context.organisation_id` and `context.deal_id`.

### DealTaskAutomationService

Location: `src/service/crm/internal/deal_task_automation_service.py`

Responsibilities:

- Load and validate the deal inside the current organization.
- Resolve assignees by exact email first, then unambiguous display-name match.
- Create a task even when no assignee resolves.
- Deduplicate by deal, source meeting, and normalized subject.
- Complete only internal editable tasks (`integration_id is None`) in the same deal.
- Write provenance into `CRMActivity.properties`.

### Worker Task

Location: `src/workers/deal_worker/tasks/deal_insight_tasks/deal_task_sync_task.py`

Responsibilities:

- Mark the `DealJobs` row in progress.
- Run `DealTaskAgent`.
- Save result data, token usage, model name, cost, and latency.
- Mark the job completed or failed.

## Data Contract

### Agent Output

`DealTaskSyncResult`:

- `created_tasks`: list of created task results.
- `completed_tasks`: list of completed task results.
- `skipped_items`: list of skipped candidates with reason.
- `failed_items`: list of tool failures.
- `created_count`
- `completed_count`
- `skipped_count`
- `failed_count`

### Task Provenance

New AI-created task rows should use:

- `source = "AI_MEETING"`
- `activity_type = "TASK"`
- `related_object_type = "DEAL"`
- `deal_id`, `related_local_id`, `related_name`
- `properties.created_via = "deal_task_agent"`
- `properties.source_event_id`
- `properties.source_association_id`
- `properties.source_summary_job_id`
- `properties.idempotency_key`
- `properties.assignee_resolution`

## Prompt Contract

The prompt should require this order:

1. Call `list_deal_tasks`.
2. Review the target meeting summary.
3. Create concrete follow-up tasks even if no owner or assignee is known.
4. Resolve ownership only when the summary provides enough evidence.
5. Complete existing same-deal tasks only when the summary explicitly states the work was done.
6. Skip duplicate or vague items.
7. Never create tasks for generic discussion points, risks without an action, or FYI statements.

## Idempotency

The service computes an idempotency key from:

- organization id
- deal id
- source association id or event id
- normalized task subject

Before insert, it searches existing same-deal tasks with either the same idempotency key or a close
normalized subject created by the deal task agent for the same source meeting.

## Completion Rules

The agent can complete an existing task only when:

- the task belongs to the current deal,
- the task is not CRM-synced read-only,
- the summary explicitly says the task/action was completed, sent, delivered, resolved, or done,
- the match is specific enough to avoid completing a different task.

If the evidence is weak, the agent skips and records the reason.

## Notification

Notification is intentionally not implemented in the first task-agent slice. The write result should
include created/completed task IDs and resolved owner metadata so a later notifier can fan out to
Teams, Slack, or WhatsApp after recipient rules are finalized.

## Tests

Coverage should include:

- task creation with resolved internal assignee,
- task creation with no assignee,
- dedupe when the same meeting summary is processed twice,
- completion of editable internal task,
- refusal to complete CRM-synced read-only task,
- registry mapping for `DealTaskAgent`,
- Celery pipeline includes task sync after the existing insight group.
